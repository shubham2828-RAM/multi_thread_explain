Introduction

Most Java developers write code that runs one instruction after another, top to bottom. That's single-threaded code, and it's easy to reason about — there's only ever one thing happening.

But real programs often need to do several things at once: handle multiple web requests, keep a UI responsive while loading data, or use every core on a machine to finish work faster. That's where threads come in.

This course builds up from "what is a thread" to the tools you'll actually use — ExecutorService, locks, atomics — and finishes with the questions interviewers love to ask. Each section has a short explanation, a code example, and where it helps, a live simulation you can run yourself.

How to use this page: work top to bottom, or jump around with the sidebar. Tick a concept off once you're comfortable with it — your progress is tracked at the top of the page.
KEY TAKEAWAYS
  • Concurrency is a tool for a problem — not every program needs it.
  • Threads let one program do multiple things, sharing the same memory.
  • Most concurrency bugs come from shared data, not from threads themselves.

Program vs Process vs Thread

These three words get used loosely, but they mean specific things:

  • Program — instructions sitting on disk, doing nothing. Your compiled MyApp.class file is a program.
  • Process — a program that has been loaded into memory and is running. It has its own memory space, open files, and at least one thread. Launching java MyApp starts a process.
  • Thread — a single path of execution inside a process. A process can have many threads, and they all share that process's memory.
ProgramMyApp.class — instructions on disk, not running
ProcessLoaded into memory · own address space · PID 4021
Threadsmain() · gc-worker · http-listener — all share the process's memory
// Starting this process creates one thread automatically: "main"
public class MyApp {
    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName()); // "main"
    }
}
KEY TAKEAWAYS
  • Program → Process → Thread is a chain of "becoming more alive."
  • Processes are isolated from each other; threads inside one process are not.
  • Every Java program starts with exactly one thread: main.
03 / 33 — Foundations

What is a Thread?

A thread is the smallest unit of work the operating system's scheduler can hand CPU time to. It has its own call stack and program counter (where it currently is in the code), but it shares heap memory — objects, static fields — with every other thread in the same process.

That sharing is the whole story of this course: it's what makes threads useful, and it's also where every concurrency bug comes from.

Think of a process as an office building, and threads as employees working inside it. Each employee has their own desk (stack), but they all share the same filing cabinet (heap).
KEY TAKEAWAYS
  • Own: call stack, local variables, program counter.
  • Shared: heap objects, static fields, open file handles.
  • Threads are cheaper to create than processes, but not free.
04 / 33 — Foundations

Single-threading

A single-threaded program does exactly one thing at a time, in order. If one step is slow — reading a file, calling a remote service — everything else waits.

downloadReport();   // takes 3 seconds — nothing else can happen meanwhile
sendEmail();        // only starts after the download finishes
updateUI();         // waits its turn too

This is simple to reason about and often perfectly fine. Multithreading is not a free upgrade — it trades that simplicity for speed or responsiveness, and adds the risk of race conditions and deadlocks covered later in this course.

KEY TAKEAWAYS
  • Predictable order, easy to debug — but only as fast as the slowest step.
  • Good default for simple scripts and CLI tools.

Concurrency vs Parallelism

These are the most confused terms in this whole topic:

  • Concurrency — dealing with multiple tasks by interleaving them. A single CPU core can be "concurrent" by rapidly switching between tasks.
  • Parallelism — actually doing multiple tasks at the exact same instant, which requires multiple CPU cores.
One cashier serving two customers by switching between them is concurrency. Two cashiers each serving one customer at the same time is parallelism.

Java's threads can give you either, depending on how many CPU cores are available and how the JVM's scheduler decides to run them.

KEY TAKEAWAYS
  • Concurrency is about structure; parallelism is about execution.
  • You can have concurrency without parallelism (1 core), but not parallelism without concurrency.
07 / 33 — Foundations

How Java Threads Work

Every java.lang.Thread object is backed by a real operating system thread. When you call start(), the JVM asks the OS to create a native thread, and the OS scheduler decides when it actually gets CPU time — Java doesn't control that timing directly.

Threads within a process share the heap, but the JVM gives each thread its own stack, so recursive calls and local variables in one thread never collide with another's.

You can't predict the exact order threads run in unless you add explicit coordination — that unpredictability is a feature you have to design around, not a bug to fix.
KEY TAKEAWAYS
  • The OS scheduler, not your code, decides exact execution order.
  • Each thread: its own stack + program counter. Shared: the heap.
08 / 33 — Creating & Controlling Threads

Creating Threads

Java gives you two classic ways to define what a thread should run:

// 1. Extend Thread
class MyThread extends Thread {
    public void run() {
        System.out.println("Running in a thread");
    }
}
new MyThread().start();

// 2. Implement Runnable (preferred — keeps class free to extend something else)
Runnable task = () -> System.out.println("Running via Runnable");
new Thread(task).start();

Implementing Runnable is generally preferred: your class isn't forced to extend Thread, so it can still extend something else, and it separates "what to run" from "how it runs."

KEY TAKEAWAYS
  • Prefer Runnable (or Callable) over extending Thread.
  • A Thread object is reusable as a concept, but a single instance can only be started once.
09 / 33 — Creating & Controlling Threads

start() vs run()

This is one of the most common beginner mistakes:

  • start() — asks the JVM/OS to create a new thread, and run() executes on that new thread.
  • run() — just a normal method call. Calling it directly executes on the current thread, with no new thread involved at all.
Thread t = new Thread(() -> System.out.println(Thread.currentThread().getName()));

t.run();    // prints "main" — no new thread was created!
t.start();  // prints "Thread-0" — actually runs concurrently
Gotcha: calling run() compiles fine and often "looks" like it worked in simple tests — the bug only shows up once you rely on true concurrency.
KEY TAKEAWAYS
  • start() = new thread. run() = plain method call.
  • Calling start() twice on the same Thread throws IllegalThreadStateException.

11 / 33 — Creating & Controlling Threads

sleep()

Thread.sleep(ms) pauses the current thread for at least the given time, without releasing any locks it holds. Other threads keep running normally.

try {
    Thread.sleep(1000); // pause this thread for ~1 second
} catch (InterruptedException e) {
    Thread.currentThread().interrupt(); // restore the interrupt flag
}
Because it's a static method, sleep() always pauses the thread that calls it — never another thread you have a reference to.
KEY TAKEAWAYS
  • Sleeping does not release held locks — this can cause subtle stalls.
  • sleep() throws a checked InterruptedException you must handle.
12 / 33 — Creating & Controlling Threads

join()

t.join() makes the calling thread wait until thread t finishes. It's the simplest way to say "don't continue until this other thread is done."

Thread worker = new Thread(() -> processData());
worker.start();
worker.join();  // main waits here until "worker" finishes
System.out.println("Data is ready");
KEY TAKEAWAYS
  • join() blocks the caller, not the thread being joined.
  • You can pass a timeout: join(2000) waits at most 2 seconds.
13 / 33 — Creating & Controlling Threads

Runnable

Runnable is a functional interface with one method: void run(). It describes a task with no return value and no checked exceptions — "just go do this."

Runnable task = () -> {
    System.out.println("doing work...");
};
new Thread(task).start();
KEY TAKEAWAYS
  • No result, no checked exceptions — use Callable if you need either.
  • A Runnable is just data until something (a Thread or executor) runs it.
14 / 33 — Creating & Controlling Threads

Callable and Future

Callable<V> is like Runnable but can return a value and throw checked exceptions. Submitting one to an executor gives you back a Future<V> — a placeholder for a result that isn't ready yet.

ExecutorService pool = Executors.newFixedThreadPool(2);

Callable<Integer> task = () -> {
    Thread.sleep(500);
    return 42;
};

Future<Integer> future = pool.submit(task);
System.out.println("doing other things while task runs...");
Integer result = future.get();  // blocks until the value is ready
KEY TAKEAWAYS
  • future.get() blocks — call it only when you actually need the value.
  • Future also exposes isDone() and cancel().
15 / 33 — Shared State & Safety

Shared Memory

All threads in a process read and write the same heap. That's what makes threads powerful — they can collaborate on the same data — and it's also the root of nearly every bug in this section of the course.

class Counter {
    int value = 0; // lives on the heap — every thread sees the same "value"
}
If two threads never touch the same mutable data, they can't race — that's why immutable objects and thread-local data are two of the easiest ways to avoid these bugs entirely.
KEY TAKEAWAYS
  • Shared mutable state is the single root cause behind races and most deadlocks.
  • No sharing → no race, by definition.

Race Condition

A race condition happens when the result of your program depends on the unpredictable timing of threads. The classic example: two threads incrementing the same counter using value++, which is actually three steps — read, add one, write back — not one atomic step.

int value = 0;
// value++ is really:
int temp = value;     // 1. read
temp = temp + 1;        // 2. add
value = temp;         // 3. write

If two threads interleave those three steps, one increment can be lost. Run it below — with 2 threads each doing 5,000 unsynchronized increments, the shared counter almost never lands on the mathematically expected 10,000.

Pick a mode above to run 2 threads × 5,000 increments each.
This demo simulates the interleaving in JavaScript to visualize the effect — the real cause in Java is identical: a non-atomic read-modify-write on shared memory.
KEY TAKEAWAYS
  • value++ is not atomic — it's read, modify, write.
  • Race conditions are often intermittent, which makes them hard to catch in testing.
17 / 33 — Shared State & Safety

Critical Section

A critical section is any block of code that touches shared, mutable state and therefore must not be run by more than one thread at the same time. Everything outside it is safe to run freely in parallel.

void deposit(int amount) {
    // -------- critical section starts --------
    balance = balance + amount;
    // -------- critical section ends ----------
}
Good concurrent design keeps critical sections as small as possible — the less code that has to be serialized, the more real parallelism the rest of your program keeps.
KEY TAKEAWAYS
  • Only shared, mutable, accessed-by-multiple-threads code needs protecting.
  • Smaller critical sections mean less contention and better throughput.
18 / 33 — Shared State & Safety

synchronized

The synchronized keyword protects a critical section using a built-in, per-object lock (a "monitor"). Only one thread can hold that lock at a time — every other thread that wants it simply waits.

class Counter {
    private int value = 0;

    public synchronized void increment() {
        value++;  // only one thread here at a time, guaranteed
    }
}

You can synchronize a whole method (locking this), or just a block using any object as the lock — useful when you only need to protect part of a method.

private final Object lock = new Object();

void increment() {
    synchronized (lock) {
        value++;
    }
}

Two threads calling a synchronized method — Thread-2 must wait for the lock.

Thread-2
Idle.
KEY TAKEAWAYS
  • Every object has an intrinsic lock; synchronized just uses it.
  • Locking too broadly kills parallelism; too narrowly reintroduces races.
19 / 33 — Shared State & Safety

volatile

volatile guarantees that reads and writes to a field go straight to main memory, so every thread always sees the latest value — no thread keeps a stale, cached copy.

private volatile boolean running = true;

void stop() { running = false; }  // called from another thread

void loop() {
    while (running) { doWork(); } // will actually see the update
}
What volatile does not do: it does not make compound actions like count++ atomic. It solves visibility, not race conditions on multi-step operations — for that you still need synchronized or an atomic class.
KEY TAKEAWAYS
  • Fixes visibility across threads, not atomicity of multi-step operations.
  • Classic use case: a boolean "stop" flag checked in a loop.
20 / 33 — Shared State & Safety

Atomic Classes

java.util.concurrent.atomic gives you classes like AtomicInteger and AtomicLong that perform operations like increment-and-get as a single, indivisible hardware-backed step — no lock required.

AtomicInteger counter = new AtomicInteger(0);

counter.incrementAndGet();       // atomic, no synchronized needed
counter.compareAndSet(5, 10);   // "if it's still 5, set it to 10"

Under the hood these use a CPU instruction called compare-and-swap (CAS): try the update, and if another thread changed the value in the meantime, retry — no thread ever blocks waiting.

KEY TAKEAWAYS
  • Lock-free, usually faster than synchronized for simple counters.
  • Only covers a single variable — not a substitute for locks across multiple fields.
21 / 33 — Shared State & Safety

Locks / ReentrantLock

ReentrantLock does the same job as synchronized, but as an explicit object with extra abilities: it can time out while waiting, be interrupted, or be acquired in a non-block-structured way.

ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    value++;
} finally {
    lock.unlock();  // always release in a finally block
}
The one rule that matters: every lock() must be paired with an unlock() in a finally block. Unlike synchronized, the compiler won't release it for you.
KEY TAKEAWAYS
  • tryLock(timeout) lets a thread give up instead of waiting forever.
  • "Reentrant" means the same thread can acquire it again without deadlocking itself.
22 / 33 — Shared State & Safety

wait() / notify() / notifyAll()

These let threads coordinate on a condition, instead of "spinning" and repeatedly checking it. A thread calls wait() inside a synchronized block to release the lock and sleep until another thread calls notify() or notifyAll() on the same object.

synchronized (queue) {
    while (queue.isEmpty()) {
        queue.wait();  // releases the lock, sleeps until notified
    }
    Object item = queue.remove(0);
}

// on another thread, after adding an item:
synchronized (queue) {
    queue.add(item);
    queue.notifyAll();  // wake up any waiting threads
}
Always call wait() inside a while loop, not an if — a thread can wake up before the condition it's waiting for is actually true.
KEY TAKEAWAYS
  • Must be called while holding the object's lock, or you get IllegalMonitorStateException.
  • Prefer notifyAll() over notify() unless you're certain only one waiter should ever wake.

Deadlock

A deadlock happens when two or more threads each hold a lock the other one needs, and neither will let go. Both wait forever.

// Thread A
synchronized (lockA) {
    synchronized (lockB) { doWork(); }
}

// Thread B — acquires the SAME locks in the opposite order
synchronized (lockB) {
    synchronized (lockA) { doWork(); }
}

🔒A
Lock A

The fix in this example: always acquire locks in the same global order (e.g. always A before B) in every thread — that alone eliminates this whole class of deadlock.
KEY TAKEAWAYS
  • Needs 4 conditions at once: mutual exclusion, hold-and-wait, no preemption, circular wait.
  • Consistent lock ordering is the most common practical fix.

25 / 33 — Pools & Practical Java

ExecutorService

ExecutorService is the standard Java API for managing a thread pool — you submit tasks, and it handles scheduling, queuing, and thread reuse for you.

ExecutorService pool = Executors.newFixedThreadPool(4);

pool.submit(() -> processOrder(orderId));
pool.submit(() -> sendConfirmation(orderId));

pool.shutdown();  // stop accepting new tasks, finish queued ones
Always call shutdown() (or shutdownNow()) when you're done — a live thread pool will keep the JVM running even after main() returns.
KEY TAKEAWAYS
  • Common flavors: newFixedThreadPool, newCachedThreadPool, newSingleThreadExecutor.
  • Never manually create raw Threads for routine background work — use an executor.
26 / 33 — Pools & Practical Java

CPU-bound vs I/O-bound

  • CPU-bound — the bottleneck is raw computation (image processing, encryption, math). More threads than CPU cores won't help; it just adds context-switching overhead.
  • I/O-bound — the bottleneck is waiting (network calls, disk reads, database queries). Threads spend most of their time idle, so you can run far more of them than you have cores.
A common rule of thumb: size a CPU-bound pool close to the number of CPU cores, and size an I/O-bound pool much larger, since most threads are waiting rather than computing.
KEY TAKEAWAYS
  • Know which kind of work you have before picking a pool size.
  • Mixing both in one pool without thought is a common performance mistake.

Thread Safety

A class is thread-safe if it behaves correctly no matter how its methods are called by multiple threads at once, with no extra coordination required from the caller. There are a few common strategies:

  • Immutability — no mutable state, so there's nothing to race over.
  • Synchronization — guard shared state with locks.
  • Confinement — keep data local to one thread (e.g. ThreadLocal).
  • Thread-safe data structures — use classes built for concurrent access.
KEY TAKEAWAYS
  • Immutable objects are automatically thread-safe — the easiest option when it's available.
  • "Thread-safe" is a property of a class's documented contract, not a guess.

Concurrent Collections

java.util.concurrent provides collections built for safe, efficient multi-threaded access — avoid wrapping a plain HashMap in manual locks when one of these already exists.

ConcurrentHashMap<String, Integer> scores = new ConcurrentHashMap<>();
scores.merge("alice", 1, Integer::sum); // atomic update

CopyOnWriteArrayList<String> listeners = new CopyOnWriteArrayList<>();
BlockingQueue<Task> queue = new LinkedBlockingQueue<>();
KEY TAKEAWAYS
  • ConcurrentHashMap — high-concurrency key/value access, no global lock.
  • CopyOnWriteArrayList — great for rare writes, frequent reads.
  • BlockingQueue — the backbone of producer/consumer designs.
29 / 33 — Wrap-up

Common Problems

  • Race conditions — unsynchronized access to shared mutable state.
  • Deadlock — threads waiting on each other's locks forever.
  • Livelock — threads keep changing state in response to each other, but never make progress.
  • Starvation — a thread never gets CPU time or a lock because others keep getting priority.
  • Memory visibility bugs — one thread's writes aren't seen by another, missing volatile/synchronization.
KEY TAKEAWAYS
  • Livelock is "busy but stuck" — deadlock is "stuck and idle."
  • Most of these trace back to shared mutable state, covered in section 15.

Final Mental Model

If you remember nothing else from this course, remember this chain:

Multiple threads → share memory → touch the same mutable data →
race condition unless protected → protect with synchronized / locks / atomics →
protecting too much, in the wrong order → deadlock risk →
manage it all sanely with an ExecutorService instead of raw threads.

Every tool in this course exists to manage one tension: threads need to share memory to be useful, and sharing memory is exactly what makes concurrency dangerous.
